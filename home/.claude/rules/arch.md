# This machine: arch (Arch Linux desktop)

- opencode runs as `opencode-serve.service` (systemd --user, port 4096) and Marcus drives it from the Tailscode iOS app. NEVER restart, stop or kill it from a session, not even detached via `setsid`: it kills the in-flight turn and he has to re-prompt. Make the config change, then tell him to hit restart in the app (new picker entries need both a server restart and a Tailscode app restart). Enforced by `~/claudeconfig/hooks/guard-bash.sh`.
- opencode API: Basic auth, user `opencode`, password `OPENCODE_SERVER_PASSWORD` in `~/.config/opencode-serve.env`. `POST /session` creates a session, `POST /session/{id}/message` sends a message.
- opencode config merges three files: `~/.config/opencode/opencode.json` (shared repo), `~/.config/opencode/opencode.local.json` (this machine's models, MCPs and instructions; Tailscode's `OPENCODE_CONFIG`), `~/opencode.json` (permissions only). Stale picker entries come from one of these; keep them consistent when adding models.
- ollama is a system service; blobs at `/mnt/nvme8tb/ollama/blobs`. GPU: RTX PRO 6000 Blackwell, 96 GB VRAM; 30B-class Q8 models load fully at 262k context with ~50 GB spare. `/etc/systemd/system/ollama.service.d/10-tune.conf` is for throughput, not capacity.
- ollama gotchas: per-model `keep_alive` in opencode options never reaches ollama, set `OLLAMA_KEEP_ALIVE` on the service; stock qwen3.x GGUF chat templates reject opencode's mid-conversation system notes on the /v1 path, patch the template with llama.cpp's `gguf-new-metadata.py` to hoist non-leading system messages (ollama#17754 fixes only the native path); `ollama create` with `FROM <model>` inherits stale PARAMETER layers, re-param from the raw GGUF blob path.
